# 下一阶段优先级（NEXT_STEPS）

> 原则：先解决实际阻塞问题，不盲目扩大架构。

## P0 — 补齐最关键的验证缺口

1. **获取合法授权的歌声素材**（自录/开放授权），完成实验 C：
   - 观察拖音、连唱、颤音下的对齐行为。
   - 至少对 1–2 首歌做**人工标注**（词/字边界），得到第一份真实歌声误差数字。
2. **实验 D**：同一首歌的「伴奏版 vs 清唱/人声版」对照，量化伴奏造成的误差。
3. **尾部修正实验**：用音频能量/VAD 对 unit `end` 做保守延展，并**用标注数据验证是否更准**（不做无依据的改动）。

## P1 — 精度改进（有标注数据后再做）

1. 引入 **blank/静音惩罚与最小/最大单元时长约束**，抑制结束时间过冲/过短。
2. 行间**全局平滑**（可选 Viterbi 或后处理），处理跨界拖音。
3. 英文：利用标点与 `'` 的模型词表特性，改进词边界；大小写/缩写映射。
4. 日文：显式建立「token ↔ 原文字符」映射表输出，便于播放器按原文高亮。
5. 中文：评估 `fa-zh` 与字符级 wav2vec2 CTC 的精度/体积权衡。

## P2 — Android 落地

1. en/ja：`torch.onnx.export` + int8 动态量化，桌面验证精度损失。
2. 接入 sherpa-onnx / ONNX Runtime Mobile 的 Android demo。
3. 用同一测试向量对齐 Python 与 Kotlin 版 Viterbi。
4. 中文单独立项（换模型或移植 fa-zh）。

## P3 — 性能与体验

1. 整曲而非逐行的批处理/缓存，减少重复前处理。
2. 长音频分块 + 滑窗，控制内存峰值。
3. 结果可视化对比工具（预测 vs 参考时间轴），加速人工标注。

## 需要你（用户）提供的东西

- 至少一首**有版权/授权**的歌曲 + 其 LRC，以及可选的干净人声轨。
- 若可能，提供该歌的人工标注逐字/逐词边界（哪怕 1 首），这是把「看起来合理」变成「有依据」的唯一途径。
- 中文模型的商业使用意向，以便确认 FunASR Model License 是否满足。
